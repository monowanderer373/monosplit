# Explicit full Reset and original-bill retagging

Status: implementation in progress, 2026-10-26 Asia/Bangkok. Not deployed or production installed. This supersedes ADR0011's carry-forward of current shared receivables/payables when the user explicitly selects the revised full Reset. Original purchases, accepted payments, identities, currencies, ownership and RLS remain protected.

The user confirmed that Reset clears both directions of old Split, without a Reset notification. Other people keep the original bills and may remove them from their own records or tag the resetting participant again. A cleared relationship has no current collectible balance on either side; retaining a bill is separate from retaining an active debt. This prevents the payer and receiver from using contradictory settlement amounts. Unrelated participants' obligations inside the same bill are not redistributed or cleared.

Full Reset records owner-period bill markers, original unpaid edge snapshots and old settlement-allocation/request exclusions atomically with the existing native opening-balance/period transaction. No fake payment, zero-value replacement expense, changed Participant, copied spending or bank debit is created. The original deterministic participant pairing and F=E−T+R operate on current obligations and actual eligible transfers. Cleared old transfers/reversals cannot create a reverse credit in the new period. Old correction descendants inherit the release until a valid new retag is accepted.

Retag is an explicit request referencing the original bill and current reset edge, not a second purchase. Only an original affected counterparty with existing bill access may request it. The resetting recipient must accept. Pending/declined retags do not contribute to debt. Accepted retags restore the unpaid amount, capped by the original source obligation. Prior actual payments remain excluded from repeat collection. New actual payments follow the existing settlement/cash RPCs. Metadata edits cannot silently erase an accepted retag, while changed source versions invalidate pending review. Superseded requests remain in history.

Removal hides only the acting user's cleared record and cannot void a bill for other participants or silently hide an active obligation. A reset emits no counterpart notification; a later explicit retag uses the ordinary compact review notification. Owner private account deductions, recurring bills and instalments continue their actual original workflows, as previously confirmed. Reference FX never becomes a deduction.

The new V2 RPC, capability marker, replay completion even for empty accounts, original preview fingerprint/locks, operation UUID and reconciliation prevent double Reset or a delayed retry clearing new activity. Legacy in-flight personal Reset receipts are reconciled honestly; they do not claim shared balances were cleared. Schema installation alone does not perform a Reset or retroactively mutate prior customer resets. No customer or owned production Reset is used for QA. Backend write tests run in disposable CI only.

The management SQL role has historically been read-only and must be rechecked before requesting one concrete installation step.
